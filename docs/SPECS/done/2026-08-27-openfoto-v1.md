## Problem

Organizing a 2519-file travel library currently means hand-written throwaway scripts. Every
existing free tool either owns the photos in a database (digiKam, PhotoPrism), needs a
Docker server (Immich), or is abandoned (Picasa). None reorganizes into plain folders, and
none offers a review-before-commit step — the step that caught two wrong faces and an
85-photo bad cluster during the manual run.

## Non-goals

- No cloud, sync, sharing, accounts, or telemetry.
- No photo *editing* — organize only.
- No RAW or HEIC in v1. JPEG and MP4 only.
- No tag hierarchies, no geotag maps. Folders are the organization.
- No mobile, no GUI in v1 (Phase 3, separate spec).
- No unattended operation on low-confidence matches — ever.

## Design

Rust workspace: `openfoto-core` (all logic) + `openfoto-cli` (arg parsing). Vault format per
ADR-0001, Rust rationale per ADR-0002, all thresholds per ADR-0003.

Central contract — every mutating command is two phases:

```
plan(&Library, &Opts) -> Plan      // pure, no disk writes
apply(&Plan, &mut Library) -> Journal
```

`Plan` is inspectable and serializable; `--dry-run` prints it and exits. A `Plan` that fails
validation cannot be applied — enforced by the type, not by a runtime check.

```
openfoto scan     [--rehash]              index; safe, idempotent, never mutates photos
openfoto dedupe   [--rmse 0.30] [--apply] burst near-duplicates -> Duplicates/
openfoto rename   [--format ...] [--apply] date-time filenames
openfoto faces    [--min-sim 0.50] [--apply]
openfoto faces review                     writes+opens HTML; reads choices back
openfoto scenery  [--max-face 0.04] [--apply]
openfoto undo     [<journal-id>]          reverse the last (or named) operation
openfoto status                           what the index knows; drift vs disk
```

Commands are non-destructive by default: without `--apply` they plan and print.

## Acceptance criteria

1. `scan` on the 2519-file fixture indexes all files with 0 errors, and completes a
   second time in under 20% of the first run's wall time (size+mtime fast path).
2. Deleting `.openfoto/` and re-running `scan` reproduces an identical index (same hash set).
3. A file renamed or moved externally between scans is re-identified by hash, not duplicated.
4. `dedupe --rmse 0.30` on the fixture yields exactly 238 groups / 284 move candidates.
5. `dedupe` never emits a cluster whose members span more than one calendar day at the
   default threshold. (Canonical regression: the 85-photo cross-day blob.)
6. `rename` is deterministic and idempotent: a second run on its own output plans zero
   changes. Names carry `_2` suffixes for same-second collisions, and `2026` survives in
   every name (the year must never be parsed as a counter).
   Against `tests/fixtures/rename_manifest.csv`: names match for the ~87% of files where
   EXIF and the camera filename agree. The remaining ~13% differ by exactly one second
   because EXIF is authoritative and the camera filename is not — see ADR-0003.
7. `rename` produces no filename duplicated anywhere in the library.
8. `rename` rejects any name containing `" * / : < > ? \ |` before applying.
9. Every move/rename carries its AppleDouble `._` sidecar; 0 orphaned sidecars afterward.
10. `faces` seeded with the 5 confirmed clusters finds >= 46 additional matches at >= 0.50,
    and assigns neither of the two known false positives (the other man, the blonde woman)
    that a 0.40 threshold accepts.
11. `faces` leaves any photo containing two different assigned people where it is.
12. Any command aborts with a non-zero exit and zero disk changes if a destination directory
    is missing at apply time. (Regression: the mid-run Finder rename.)
13. `undo` after any single command restores the exact prior hash->path map.
14. No mutating command writes to disk without `--apply`.
